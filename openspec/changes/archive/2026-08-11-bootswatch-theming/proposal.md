## Why

The site is currently styled with hand-rolled CSS (`theme/style.css`) and plain semantic markup, even though the mandated tech stack is Bootstrap 5.3.x + Bootswatch 5.3.x. The user wants the Bootswatch Vapor theme applied via Bootstrap/Bootswatch-based markup in the Jinja templates, and wants to be able to switch themes simply by pointing `site.json` at a different full stylesheet URL (default: Bootswatch Vapor).

## What Changes

- `content/site.json` gains two optional fields under `site`: `theme_stylesheet` and `bootstrap_script`, each a **full URL** (e.g., a Bootswatch CDN link). When absent, `build.py` falls back to pinned defaults (Bootswatch Vapor 5.3.3 CSS + Bootstrap 5.3.3 JS bundle from jsDelivr). No `content/` file is modified by the build.
- Templates (`templates/home.html.j2`, `templates/catalogue.html.j2`, `templates/idea.html.j2`) are restyled with Bootstrap components: navbar header, container/grid layout, breadcrumb, form-control search inputs, form-check facet controls, card-based idea/catalogue lists, and badge tags.
- `theme/style.css` is reworked to complement Bootstrap using `var(--bs-*)` tokens, keeping only the selectors that `theme/app.js` depends on (`.catalogue-card`, `.facet-item`, `.facet-items`, `.card-hidden`, `.catalogue-grid`, `.catalogue-search`, `.no-results`).
- Every generated HTML page injects the resolved theme stylesheet `<link>` (after which the local `style.css` loads) and the Bootstrap JS bundle `<script>` before `</body>`.
- Default page appearance changes (custom CSS → Vapor) and themed pages gain an external CDN dependency for styling. This is a **BREAKING** change to the self-containment contract of REQ-SO-009, so that requirement is modified to carve out an exception for the two configured theme URLs.
- No behavioral change to client-side search: the MiniSearch index, facets, catalogue filtering, URL state, and `ideas.json` payload are untouched.

## Capabilities

### New Capabilities

- _(none)_

### Modified Capabilities

- `site-output`: Add REQ-SO-011 (theme stylesheet and Bootstrap script links injected on every HTML page, sourced from `site.json` with defaults) and modify REQ-SO-009 (self-contained artifacts — explicit exception for the two configured theme URLs, which may be external CDN links).
- `build-engine`: Add REQ-BE-009 (theme resolution — read optional `theme_stylesheet`/`bootstrap_script` from `content/site.json`, apply default constants when absent, expose to template context on every render).

## Impact

- **Files updated**: `build.py` (theme constants + resolution), `templates/home.html.j2`, `templates/catalogue.html.j2`, `templates/idea.html.j2`, `theme/style.css`.
- **Files created**: none (no new templates or assets; the theme is loaded from the configured URL).
- **User-editable input**: `content/site.json` (optional `site.theme_stylesheet`, `site.bootstrap_script`).
- **Untouched**: `templates/sitemap.xml.j2`, `templates/idea.md.j2`, `theme/app.js`, `theme/assets/minisearch.min.js`, `content/ideas/*`, `site/` (regenerated by build).
- **Dependencies**: Bootstrap 5.3.3 CSS/JS bundle and Bootswatch 5.3.3 theme CSS fetched from jsDelivr at page load time (external). Still no frontend framework and no new runtime libraries for app logic.
- **Systems**: static hosting (GitHub Pages etc.) — external CDN links must be reachable by visitors; page render degrades gracefully (unstyled content) if the CDN is unreachable.
- **Constraints/Limitations/Assumptions**: assume the configured theme URL is a full, browser-resolvable URL; assume Bootstrap 5.x class semantics; out-of-scope: runtime theme switcher UI, vendoring the theme CSS/JS, and modifying any file under `content/`.
