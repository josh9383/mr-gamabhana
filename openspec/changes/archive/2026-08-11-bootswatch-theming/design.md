## Context

The site is generated by `python build.py` from `content/site.json` + per-idea `meta.json`/`meta.md`, rendered through Jinja2 templates (`templates/*.j2`) into `site/`. Styling is hand-rolled in `theme/style.css` and markup is plain semantic HTML. The mandated stack is Bootstrap 5.3.x + Bootswatch 5.3.x, but nothing uses it yet.

The user wants:
1. The Bootswatch Vapor theme applied through Bootstrap/Bootswatch-based JS/CSS styling in the Jinja templates.
2. Theme switching by specifying a full stylesheet link in `site.json` (default: Bootswatch Vapor).

Client-side search runs in `theme/app.js` (initSearchPage / initCatalogueSearch) and depends on specific element classes and IDs; any restyle must not break those selectors.

## Goals / Non-Goals

**Goals:**
- Templates emit Bootstrap/Bootswatch-based markup (navbar, container, grid, breadcrumb, form-control, form-check, cards, badges).
- `site.json` can override the theme stylesheet and Bootstrap script via full URLs; build falls back to pinned Bootswatch Vapor defaults.
- Every HTML page references the theme stylesheet and Bootstrap JS bundle; local `theme/style.css` is copied and loaded after the theme so site rules can complement it.
- All current behavior (MiniSearch facets, catalogue filtering, URL state, `?tag=`) is preserved; `theme/app.js` needs no functional changes.
- Mobile-first, responsive layout via Bootstrap grid/utilities.

**Non-Goals:**
- No runtime theme switcher UI.
- No vendoring of Bootstrap/Bootswatch into `theme/assets/` (theme is loaded from the configured URL; MiniSearch remains the only vendored asset).
- No changes to `content/`, `templates/sitemap.xml.j2`, `templates/idea.md.j2`, or the `ideas.json` payload.

## Decisions

**D1. Configuration via full-URL `theme_stylesheet` / `bootstrap_script` with build-time defaults.**
`content/site.json` may set `site.theme_stylesheet` and `site.bootstrap_script` to any full URL. `build.py` resolves each: use the configured value when non-empty, else the pinned default constants:
- stylesheet: `https://cdn.jsdelivr.net/npm/bootswatch@5.3.3/dist/vapor/bootstrap.min.css`
- script: `https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/js/bootstrap.bundle.min.js`
The resolved values are merged into the `site` dict and every template accesses them via `{{ site.theme_stylesheet }}` / `{{ site.bootstrap_script }}`.
Rationale: user's explicit requirement ("specify stylesheet link in full"), trivially reversible, no build restructure.
Alternatives: vendoring each theme into `theme/` (rejected — defeats the "switch by link" requirement); a short theme name + lookup table (rejected — user wants full links).

**D2. Theme link injection order and placement.**
`<head>`: theme stylesheet `<link>` first, then local `site/assets/style.css` so site rules override theme/Bootstrap defaults. Before `</body>`: Bootstrap JS bundle `<script>` then `assets/app.js`. No inline styles or inline scripts anywhere.
Rationale: local CSS must win for app.js-dependent selectors; app.js must run after the DOM it binds.

**D3. Preserve the exact app.js selector contract.**
Templates keep these hooks unchanged: `#search-page`, `#search-input`, `#search-results`, `#result-count`, `#clear-facets`, `.facets`, `.facet[data-facet=…]`, `.facet-items`, `.catalogue-grid`, `.catalogue-card`, `.catalogue-search`, `.card-hidden`. app.js injects `.facet-item` labels and `.catalogue-card` anchors with template literals — Bootstrap classes are added only in the templates, and `theme/style.css` restyles the injected elements using `var(--bs-*)` so they look native.
Rationale: guarantees zero functional regression in search/facets.

**D4. Bootstrap component mapping per template.**
- Header: `<nav class="navbar navbar-expand navbar-dark bg-primary">` with a `.navbar-brand` link to the root (title).
- Main shell: `<main class="container py-4">`; headings use `<h1 class="h2">`.
- Breadcrumbs: `<nav aria-label="breadcrumb"><ol class="breadcrumb">` with `.breadcrumb-item` items.
- Search inputs: `form-control` class; facet checkboxes/labels use Bootstrap `form-check`/`form-check-input`/`form-check-label` classes combined with the existing `.facet-item` hook.
- Cards: idea/catalogue cards get `card` + keep `.catalogue-card`; grids use `row g-3` + keep `.catalogue-grid`.
- Tags on idea pages: `.badge` pills in a `.d-flex flex-wrap gap-2` container.
- Facet heading text uses Bootstrap heading utilities.

**D5. `theme/style.css` rework on top of Bootstrap variables.**
Remove hand-rolled layout (body margins, header bar, page width, buttons). Keep only app.js-dependent rules: `.catalogue-card`, `.facet-item`, `.card-hidden`, `.catalogue-grid` (grid fallback), `.no-results`, `.facet h3`, `.facet-actions` — all expressed with `var(--bs-*)` (e.g., `--bs-border-color`, `--bs-body-bg`, `--bs-link-color`, `--bs-body-color`) so the look follows the active theme automatically.
Rationale: single visual source of truth becomes the theme stylesheet; local CSS only supplies the layout glue the JS needs.

**D6. REQ-SO-009 self-containment exception.**
Self-containment ("every page SHALL reference only assets under the site's own base_url path") conflicts with external theme URLs. The requirement is modified to exempt the two configured theme URLs; everything else (local assets, cross-page independence) stays strict.
Rationale: the configurable full-URL theme is an explicit user requirement; the exception is narrow and documented.

## Risks / Trade-offs

- [External CDN dependency: themed pages need network for styles/JS] → pinned versioned defaults on jsDelivr; content remains readable unstyled if CDN is down; user can repoint `theme_stylesheet`/`bootstrap_script` to self-hosted files without code changes.
- [Restyle regresses app.js behavior] → D3 selector contract preserved verbatim; verified in tasks by grepping generated pages and running the headless search smoke test.
- [Bootstrap JS bundle adds page weight and a few global behaviors] → bundle is only wired to navbar/collapse interactions already present; app.js does not depend on it.
- [Broader browser styling shifts] → Bootstrap resets are applied site-wide; acceptance is the mandated stack, verified against the Vapor default.

## Migration Plan

No content migration. The build defaults to Vapor, so existing `content/site.json` (no theme fields) still builds a fully styled site. To switch themes, edit `content/site.json` and run `python build.py`. Rollback: remove the fields (restore defaults) or revert the previous values and rebuild.

## Open Questions

None blocking. Minor: whether Bootstrap JS is needed on idea pages (no interactive components there) — decision: include everywhere for consistency and future-proofing, per D2.
