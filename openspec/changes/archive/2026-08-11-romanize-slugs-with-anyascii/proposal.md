# Romanize Slugs With AnyAscii

## Why

Currently `slugify()` in `build.py` preserves Devanagari characters, producing URLs like `/boards/महाराष्ट्र-राज्य-मंडळ/` and `site/boards/महाराष्ट्र-राज्य-मंडळ/`. Devanagari in file paths and URLs is awkward to share, link, and inspect, and folder names must exactly match URL slugs. Romanizing slugs to ASCII via `anyascii` keeps file/folder names and URL paths consistent and shareable, and the transliteration is reversible (`anyascii` provides the romanization that can be mapped back to the original script).

## What Changes

- **BREAKING**: `slugify()` in `build.py` romanizes input with `anyascii` before slugging. Non-ASCII Devanagari input now yields ASCII romanized slugs (e.g., `कोन` → `kon`, `महाराष्ट्र राज्य मंडळ` → `mharastr-rajy-mmdl`).
- **BREAKING**: All generated URLs, canonical URLs, sitemap entries, and `site/` directory names change to the romanized slugs for any value containing non-ASCII characters.
- Add `anyascii` to `requirements.txt`.
- `theme/app.js` is unaffected (catalogue filtering operates on `data-search` text and card titles, not slugs).
- Content files (`content/ideas/{id}/meta.json`, `meta.md`) are unaffected; idea `id`s are already ASCII.

## Impact

- Files updated:
  - `build.py` (`slugify()` function)
  - `requirements.txt` (add `anyascii`)
  - `README.md` (note romanized slugs / URLs)
- Regenerated output: `site/` — every folder, canonical URL, and sitemap URL derived from Devanagari metadata changes.
- No change to templates, theme assets, or the client-side payload shape.
- Constraint: `slugify` must still collapse to `item` when romanization yields an empty result, preserving the existing fallback contract.
